1. 项目概述

Pi Web 是一个 Next.js（App Router）+ React 构建的本地优先（local-first）AI 编码代理前端。它本身不运行大模型推理，而是通过本地子进程托管 @earendil-works/pi-coding-agent SDK，把浏览器 UI 与进程内的 Agent 会话桥接起来。

核心特征：

  • 会话浏览是只读的：读取 ~/.pi/agent/sessions/*.jsonl 不创建任何 AgentSession。
  • 发送消息才会激活会话：startRpcSession() 在进程内创建一个 AgentSession 并常驻于全局注册表。
  • 事件通过 SSE 回流：Agent 产生的流式事件经 SSE 推送回浏览器，再由 useAgentSession 做消息合并与分支协调。
  • 文件系统是单一事实来源：.jsonl 文件可整体重写，parentSession 仅为展示元数据。

Core 3.3 AgentSession 层 lib/rpc-manager.ts

这是整个系统的枢纽。关键事实：

  • 每个 session id 对应一个 AgentSessionWrapper，键存于 globalThis.__piSessions。globalThis 能跨 Next.js 热重载存活，普通 module 级 Map 不行。
  • 并发的 startRpcSession() 调用共享同一个 start Promise（globalThis.__piStartLocks），避免重复创建。
  • 空闲超时 10 分钟自动销毁。
  • fork 必须立即销毁 wrapper：AgentSession.fork() 会就地改写 wrapper 内部状态为新会话 id；若不立即 destroy()，后续请求会拿到已被 fork 的状态，导致 parent 链损坏。修复方式为 send("fork") 捕获 newSessionId 后先 this.destroy() 再返回。

Storage 3.4 数据与持久化层 ~/.pi/agent/

  • sessions/*.jsonl：聊天 + 工具调用 + 分支的唯一事实来源。
  • 文件可整体重写（pi 自身迁移时也是如此），parentSession 仅是展示元数据，不影响内容。
  • 删除会话级联重挂子节点（reparent）时也直接写文件。
  • settings.json 提供 defaultModel；models.json 描述模型与 provider。

两种"分支"不要混淆：
• Fork（用户消息上的 Fork 按钮）：创建新的独立 .jsonl 文件，在侧边树中作为子节点显示（通过 header 的 parentSession 字段）。

5. 关键设计决策与陷阱

主题决策 / 陷阱处理
注册表存活 Next.js 热重载会重置 module 级变量，导致会话丢失。 会话存 globalThis.__piSessions。
Fork 状态污染 fork() 就地改写 wrapper 内部状态为新 id。 send("fork") 捕获 newId 后立刻 destroy()；下次请求按原 id 重新加载干净会话。
工具字段归一化 pi 存为 {id, name, arguments}，而 ToolCallContent 用 {toolCallId, toolName, input}。 normalizeToolCalls() 在文件加载和流式处理两处调用。
新会话工具预设 工具名在创建时通过 toolNames[] 传入；已有会话挂载时由 get_tools → getPresetFromTools() 推断。 完全禁用工具时，rpc-manager 传入空许可列表并在启动/重载/资源发现后强制 systemPrompt = ""。
默认模型 新会话默认模型来自 ~/.pi/agent/settings.json。 GET /api/models 返回 defaultModel，ChatWindow 挂载时预选。
会话文件可重写 parentSession 仅为展示元数据，不影响内容。 级联重挂子节点时可直接 writeFileSync 整文件。
不要做的事：开发期禁止运行 next build——它会污染 .next/ 并破坏 npm run dev。启动用 npm run dev（随机端口），类型检查用 node_modules/.bin/tsc --noEmit，Lint 用 npm run lint。

7. 开发约束

  • 进入仓库先读 AGENTS.md。
  • 所有项目用 lrnev 管理，并配置好对应 MCP 与项目记忆（见仓库约定）。
  • 进入仓库按运行目录自动 lrnev init（若 .lrnev 尚未初始化）。
  • 按用户明确指示执行，不自动选任务、不排程、不自行决定下一任务；多任务按顺序完成「实现 → 验证 → 日志追加」闭环。
  • 只做当前 scope 内改动；跨 scope 须用户明确要求并在汇报中说明。
